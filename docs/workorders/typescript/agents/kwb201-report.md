## Causes, fixes, tests (red first, then green)

1. Transcript read on every Pre Bash call (no-find, suite-once; `lastPrompt` in lib/turn.mts, finding 1 of review w10-tests).
   - Fix: `lib/last-prompt.mts` (new): the answer is kept by transcript path with size, mtime and the offset after the last whole line; a later call reads only the appended bytes; a shrunk file, or one with a new mtime at the same size, is read again. The first call reads from the end in 1 MB pieces into one buffer and looks at each line's bytes: a line with no `"user"`, or holding a `"type":"tool_result"`, is never decoded, so the 25 MB read makes no strings (first version decoded every piece: 16 workers then held 770 MB; this one 560). `lib/prompt-of.mts` (new) holds the entry types, `realPrompt` and `promptOfLine`; turn.mts imports them and re-exports `lastPrompt` and `TranscriptEntry`. Used by the daemon's workers and the TypeScript runner alike (same module).
   - Test: test/unit/hooks-lib/last-prompt.test.mts (4 cases: second call on a 30 MB transcript reads 0 bytes; an appended 1 KB is read as 1 KB and a new prompt replaces the old, hook feedback does not; a half-written line is read when whole and a truncated file is read again; no prompt or no file gives ''). Red: module did not exist. Green: 4/4; first call on 30 MB: 48 ms. Integration: test/integration/live-event-speed.test.mts first case, red `Bash p50 28 ms` (scratch with 25 MB transcript), green 2 to 3 ms.
2. once-only and template-law read, stat and write back a whole index per call.
   - template-law: `lib/asked-index.mts` (new): the hook is async; it names the statement hashes, `shape:<id>` and `def:<name>` keys of what the event writes and gets back, through `ctx.candidates`, only the files that share one (`FileStatements` gained optional `shapes`, `defs`, `windows` in lib/near-copies.mts, so types.d.mts needed no change). Files under tests or skipped folders are taken out of the answer (`without`, folder by folder as codeFiles does). A write in a worktree, or no daemon, falls back to `repoIndex` as before. `resident/index.mts` answers with a key to files map built with the index (no walk of every file per question) and builds the repetition index only when asked a non-`dup:` key.
   - The one-shot runner's `repoIndex` (lib/repo-index.mts): keeps what it last held per process, and writes the file only when a file changed or the file count did (was: whole read, stat of every file, whole write, every call).
   - once-only is not on the repetition index: it uses lib/dup-index.mts (window hashes), so `ctx.candidates` with statements could not serve it. Its keys are `dup:<hash>`. dup-index.mts was split (tokenizer to lib/dup-tokens.mts, candidate matching to lib/dup-match.mts: matching now takes "hits" (hash, token, line, end line) so the other files can come from memory or from a message); `judgeCopyWritesAsked` asks `ctx.candidates`; `resident/dup-windows.mts` (new) holds the one dup index on the main thread, brought up to date after a PostToolUse and changed only for files that moved, one number per window (file * 2^24 + token; a first version with a four-number array per window cost 130 MB more on the kit's repo). once-only's `copiesIn` is async; a write in a worktree still reads the checkout's own index. once-only-index (recorder) skips the main checkout when a daemon is asking, since the daemon holds that index (the persisted file is then not refreshed during a daemon session: a runner that takes over after the daemon ends re-reads the files that changed, stat-keyed, as it always did for files newer than the file).
   - Tests: test/unit/hooks-lib/index-cost.test.mts: template-law judges by what the daemon answers (a daemon answering [] passes a write the disk would refuse; the real answer refuses it), tests/skipped folders in the answer are no copy, the one-shot runner writes the index only when a file changed (red: rewritten every call), the main thread's dup index finds the same clone as the in-process index (deep equal) and drops a changed file's windows. Existing dup-index unit tests (clonesIn, tokenize, windows, WINDOW) and the once-only, once-only-index and template-law selftests and worktree cases are green.
   - Live-like result: Write p50 65 to 4 ms in the kit scratch; in the scratch rig (300 files, 25 MB transcript) Write p50 was already 34 ms before this change (300 files is small) and stays 34 to 35 ms, so the test's Write bound (110) did not go red; its Bash bound (20) did.
3. git-guard's 536 ms Pre Bash worst: explained, not changed. The slow calls in the kit's own hooks.log are `git commit` and `git push` Bash calls: law 9 (no commit while earlier commits are not on GitHub) needs GitHub's branch heads, kept at most a minute (lib/remote-heads.mts `remoteHeads`), and the call that finds the kept look old pays a `git ls-remote --heads` over the network (log lines from this session: 196, 301, 780, 1092, 1210, 1367, 1680 ms on commit and push calls; 0 ms on every other git-guard call). That is a network round trip in a law that needs the answer before the commit; not a hook cost of every call. To avoid it the look would have to be refreshed in the background before it is needed (the Stop path already does, `refreshLater`), which changes when the law sees a push; left to the lead. The git-guard selftest "kept Stop look ... within about a second of GitHub" failed once under the load of a 285-test run (154 s) and passed in the later full-gate runs: load-sensitive, not caused here.
4. Daemon RSS. After 1: the kit's scratch daemon 624 to 372 MB; the scratch rig under a 32-wide burst 1,091 to about 500 MB. A per-worker old-space cap (`maxOldGenerationSizeMb` 64, then 32) and a full collection by an idle worker were tried and measured: no change in RSS (cap 64: 770 to 770; cap 32: 543 to 543; idle collection: 542 vs 536, V8 heap after it 7 to 18 MB a worker). Not shipped (a cap also risks a worker running out of memory on a hook that reads a big file, such as the Stop hooks that read a whole turn). The floor is not the hooks: the scratch daemon with its 16 warm workers and one event served is 176 to 183 MB, and a first round of 16 busy workers adds 300 MB (about 20 MB a worker: hook modules, JIT code, regexes), vmmap of the daemon after a burst: 538 MB footprint, V8 pages 410 MB, malloc 80 MB; the node binary's own text counts 227 MB of the resident figure. So "16 workers busy, 1,000 events, under 250 MB" is not reachable by a heap cap or a collection in this build; it needs fewer warm workers (the default is 16 warm; 8 saves about 80 MB idle, the order's d-29 note) or fewer hooks per worker. That is a W8 design decision I did not take. The test holds what is measured: warm pool under 250 MB (176), 16 busy workers over 1,024 events under 650 MB (471 to 585; 1,091 before). Red before the work: the earlier build gave 909 to 1,091 MB at 32-wide, over 650. Note that 32 concurrent events grow the pool to 18 to 23 workers.
