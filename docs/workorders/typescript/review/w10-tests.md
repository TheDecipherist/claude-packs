# W10 review: the tests and what a project pays

Reviewer slice: tests that lost assertions, hooks over their budget, the pack-content ratchet, the daemon's memory.
Nothing was fixed. Base: work/2.0.0-typescript at aabf300; originals at e35a0d2. Size: S under an hour, M a few hours, L a day or more.

## Findings, most serious first

### 1. Two Pre Bash hooks re-read the whole transcript on every call: 115 to 140 ms each, and about 30 MB of worker RSS per call (S/M, serious)
- Where: `packs/base/hooks/lib/turn.mts` `lastPrompt` and `tailEntries`, called by `packs/base/hooks/no-find.mts` and `packs/base/hooks/suite-once.mts` (`hook`).
- What: `tailEntries` reads the last 1 MB of the transcript, then 4 MB, 16 MB, 64 MB, until it finds a user prompt. In an unattended run one turn is the whole run, and tool results are not prompts, so the prompt sits far back and every Bash call reads, decodes, splits and JSON-parses megabytes. Both hooks do it on every Pre Bash call, so the same file is read twice per call.
- Evidence (the kit's own `.claude/hooks.log` since the lock's `updated` 2026-11-12T03:02:48Z, read with `budgetProblems` itself): over 174 Pre Bash calls `suite-once` averaged 143 ms and `no-find` 142 ms, every other hook 0 to 30 ms (`kit-lock` 75, `git-guard` 30, `heartbeat` 25). The event's wall is 142/173 ms p50/p95 against a budget of 100/250, so Pre Bash p50 is over budget on exactly these two hooks. doctor reports: no-find 138/159 (worst 222), suite-once 139/162 (worst 223), both over 10/50 and the 200 worst.
- Measured: one worker thread, `no-find` loaded, six calls with `transcript_path` set to the 25 MB transcript of this repo: 114 to 127 ms a call, worker heap 6 -> 36 MB, **process RSS 24 -> 205 MB** (the buffers and strings land in old space, since the worker's young generation is capped at 1 MB; V8 does not hand it back). This is the cause of the daemon's RSS in this repo (finding 5), not the loaded hooks.
- Fix: read the turn start once per transcript and keep it: a module-scope (or daemon main-thread) cache of `{path, size, startOffset}`; on the next call read only the bytes after the cached size, and re-scan only when a new prompt entry appears. The two hooks then share one lookup. Alternatively the daemon passes `lastPrompt` in the context. Add a test with a transcript of 30 MB whose prompt is at the start, asserting the second call reads under 1 MB (a counted `readSync`).
- Size: M (S for the module cache alone, M with the incremental read and its test).

### 2. Pre Write is over budget on once-only and template-law, each re-reading and rewriting the whole repetition index per write (M)
- Where: `packs/base/hooks/lib/repo-index.mts` `repoIndex` (reads the whole index JSON, walks every code file with `statSync`, writes the whole JSON back with `writeJson` on every call); called by `once-only.mts` (through `lib/dup-index.mts` `judgeCopyWrites`) and `template-law.mts` (line 105, `repoIndex(root, ...)`).
- Evidence: Pre Write wall 84/329 ms (p50/p95 of 42 calls) against 120/300: p95 over. `once-only` 81/326 (worst 362), `template-law` 5/69 (worst 83) against 10/50 and worst 200.
- What: the daemon's main thread has an index (`resident/index.mts`) that workers ask by message, but these two hooks do not use `ctx.candidates`; they each do the whole-file read, a statSync per file (691 files in the kit), and a whole-file write, in a worker. `resident/index.mts` `candidates` also builds `Object.entries(fresh())` for every query, one array of every file per ask. Measured: `repoIndex` over the kit takes 200 to 340 ms cold and holds about 5 MB; warm cost was not separately measured.
- Fix: route both hooks through `ctx.candidates` when present (the field exists for this), keep the file index only for the one-shot runner, and write it only when an entry changed (`writeJson` only if any `now[rel]` is new).
- Size: M.

### 3. git-guard has a 536 ms worst call at Pre Bash (S, read only, not reproduced)
- Where: `packs/base/hooks/git-guard.mts`, its git look (`lib/stop-look.mts`, `lib/remote-heads.mts`).
- Evidence: p50/p95 0/0 over 100 calls, worst 536 over the 200 budget; doctor reports it as a budget problem. The cost is an occasional uncached `git` child process on a Bash call that mentions git, not a cost of every call. - Fix: log which child ran (a `late` note on that call) before changing anything; then cache the look per `.git` mtime for the call's window. Size: S to find, S to fix.

### 5. The daemon's memory (d-29, KWB-197): from the code, and measured
What a worker holds after every hook once, from `packs/base/hooks/resident/worker.mts` and `pool.mts`:
- A worker is a thread with its own V8 isolate; hooks and their `lib/` imports are loaded per worker (a module graph is not shared between isolates). `ensure(name)` imports a hook the first time it is asked for it and `loaded` keeps it for the worker's life (until `recycleAfter` 500 events, or the 10 minute idle reap of workers beyond `warm`).
- Measured on a scratch base install (30 hooks) and on a copy of the kit's own `.claude` (40 checks, 21 rules, 30 hooks), nothing running but my harness, which started the real `worker.mjs` with the pool's `resourceLimits`:
  - one idle worker: RSS +8 MB (isolate and bootstrap);
  - one worker after every hook ran on five event kinds: +5 MB more (heap used 4.5 -> 9.0 MB, 20 more rounds only to 9.7 MB: no cache grows with use);
  - 16 workers idle: +127 MB; 16 workers each having run every hook: 223 MB (scratch) and 228 MB (kit copy); 16 preloaded: 201 MB. That is the 225 to 247 MB of d-29.
  - the biggest per-hook costs are `inside-the-project` 1.5 MB and `lesson-checks` 0.7 MB; the module-scope caches in `lib/glob.mts` and `lib/shape-prose.mts` are small.
- The repetition index is the main thread's, not a worker's: 17,108 statements in 691 files held 5 to 6 MB heap in this repo.
- So loaded modules and the index do not explain the 748 MB the kit's own daemon holds now (pid 67925, 24 threads, RSS 748 MB, read with `ps`). What does is finding 1: a worker that reads a 25 MB transcript keeps about 180 MB of it. Large reads in any hook (transcripts, `git` output, whole files) land in old space because `maxYoungGenerationSizeMb: 1` makes every large allocation promote, and RSS is not returned.
- What would cut it most, in order: (a) the transcript cache of finding 1 (removes the dominant term, measured); (b) a hook that reads a large file does it on the main thread once and answers by message (the pattern `candidates` already has), or streams it; (c) `resourceLimits.maxOldGenerationSizeMb` per worker (say 48) so V8 collects before growing, at some CPU; (d) recycle a worker after a hook reports a large read, not only after 500 events; (e) a smaller pool: 8 instead of 16 saves about 80 MB idle in a scratch repo but costs the event times W8 exists for, so last; (f) unloading idle hooks saves about 5 MB a worker at most, not worth the code.
- Verification note: I could not attach to the kit's running daemon (the brief forbids touching it), so the 748 MB is its RSS from `ps` and the cause is a measured reproduction on a copy, not a heap snapshot of it. Size to fix (a): M.

### 6. noop's oracle is no longer independent (M)
- Where: `test/integration/noop.test.mts`, `test/fixtures/noop/*/expected/settings.json`, `packs/manifest-2.0.0.json`.
- Old (`test/noop.test.mjs`): hand-written `CHANGED` and `REVIEWED` lists, each file with the reason it changed; the update's output had to equal the 0.9.15 kit's.
- New: the manifest of files and hashes is written by `scripts/counts.mts` from the same install code it judges (`readManifest`, `updatedProject`), and W8.1 regenerated `expected/settings.json` to the new runner form. A change to an installed file is red until someone regenerates the manifest; regenerating it is one command with no reason attached. The four old assertion messages "the same files, no more, no fewer", "only the base files changed on purpose differ in content", "the same files, and the listed new ones", "only the listed files changed" survive only as `drift(...)` equal to `[]` against a file the kit writes itself.
- Fix: keep the manifest, but require each manifest change to name its reason (a `reasons` map in the manifest the generator preserves and a test that a changed hash without a reason is red), and leave `expected/settings.json` as it was with a separate expected file for the runner form. Size M.
