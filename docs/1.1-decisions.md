# 1.1.0 decisions

The user was away for this work, so each choice below is the recommended one, taken without asking.

## Group 1: what fails silently or fails open

- **d-1, a crash refuses once.** A hook that crashes on PreToolUse or PostToolUse makes the runner exit 2 and name the crash. The same call again goes through, logged as unjudged. Always refusing would let one broken hook stop all work, including the write that fixes its config. Always passing is the fault itself (KF-18). On Stop, UserPromptSubmit and other events nothing is refused: the author is told by a `systemMessage`.
- **d-2, a crash is its own log.** New crashes go to `.claude/logs/crashes.jsonl`. Old entries in `refusals.jsonl` with a code other than 2 are read as crashes, so old logs are never rewritten.
- **d-3, clearing a crash.** `logs clear <hook>|all fixed|superseded "<why>"` adds a line to `verdicts.jsonl`. It clears crashes up to that moment, and a later crash is red again. A crash older than the hook or any file in `hooks/lib/` is history without a mark, so an update that fixes a shared lib clears it.
- **d-4, what answers a rule's test.** A test, bench or gate file that names the rule, or `ruleTests` in `layout.json`, which may decline with a reason. A rule counts only once it governs a source file the project wrote, so a new project is not red. Text matching alone cannot prove a test does what the Check says: it proves the test was thought of.
- **d-5, what an install reports.** The rule-test and parameter-lock findings are notes at the end of `init`, `add`, `update`, `new` and `config`, and red in `doctor`. An install on existing code has not failed; a project asked about its health is told.
- **d-6, git-guard for a new install.** `init` writes `house: true`, `ghAuth: cli`, `trunkNeedsYes: true` into a layout it creates. `update` and a re-init leave a layout alone. `DEFAULTS` stay, so an existing `house: true` project is held exactly as before, except that `GH_TOKEN=$X` is now refused when X is unset and the command loads nothing. A project that sets the variable only in a shell profile must load it in the command or set `ghAuth: cli`.
- **d-7, one shell reader.** `once-only` refused the hand copy in `global/hooks/lib/`, and rightly. `global add` now installs from `packs/base/hooks/lib`, and `global/` keeps a one-line re-export so the hooks run from the kit's folder.
- **d-8, shell edits of source, a slip of this session.** Early in group 1 some source edits went through a Python script outside the project, which no hook reads. All such files were then fired as writes through the hooks on a copy of `origin/main`: 11 judged, 0 refused. Source edits after that use Write and Edit, with the slips in d-16.

## Group 2: false refusals

- **d-9, two right marks are overturned.** `d2c1b74b` and `9612825c` were marked right and now pass. Their words, `PROGRAM knob` and `EDIT knob`, were marked wrong in `6ed8a084` and `9c85212b`, so the log disagrees with itself, and the panel report says the two marks had loose reasons, logged as KF-36. Every other right refusal stays refused. The fixture names the two, and a test holds that they are the only ones.
- **d-10, what the real refusals cannot prove.** Five right refusals are new-type or selector findings (`4273cfbd`, `a1872e7d`, `fe65842a`, `9e689ecf`, `50b81a2f`). They need a whole file and an earlier manifest, and the log keeps neither. That code is unchanged, and its selftest cases hold it. So 8 right refusals are replayed, not 15.
- **d-11, a count against an index.** The declared parameter decides, as KF-17 asks. `turnProgram (int steps, ...)` and `turnEditKnob (int knob, ...)` differ only there. A call with no declaration in the project stays an instance.
- **d-12, a source tag alone excuses nothing.** `[MAN] ... bank 6 to bank 10` was marked right, so the tag cannot be the test. A number passes only in a comment with a tag and a role verb after it (`knob 1 selects`).
- **d-13, KF-34's cause is not the one reported.** The report blames the fast-forward. The transcript shows no write by it: compaction is not a prompt, so one turn held the whole run, and the In progress line named only the last step. The fix is a landing ending what a turn answers for, by the same test the fault asked for.
- **d-14, KF-33.** making-check skips the detector for tool writes when `once-only` is installed, since those writes already passed it. Shell writes stay judged. What remains, about 280 ms of 353 on a 23 MB transcript, is parsing it, left as it is: under the line, and a long session's cost.
- **d-15, `dispatch-once` gains a law.** KF-35's refusal was marked right for a false reason: the file held two switches on one kind, which is the true fault. So two switches on one kind in one new file are now refused, and say so.
- **d-16, shell edits again.** Selftest rows in group 2 and the moved `git-guard` selftest went in by script, against what d-8 says. Every changed source file of the branch was then fired through the hooks, as in d-8: 17 judged, 1 refused. The one is `shape-lists.mjs`, refused as a copy of `handLists` in `shape.mjs`, which is the moved code as it stands on the copy of `origin/main`; on the branch that copy is gone.

## Group 3: new projects

- **d-17, the queue is per project.** Nothing but `global add` goes in `~/.claude`, so `buildq` ships in `.claude/tools/`, and its slots live in the machine's temp folder, so they still hold across projects. A `buildq` on the path is still accepted.
- **d-18, a wrapper that queues nothing is a doctor finding, not a refusal.** A new refusal would switch on silently in existing projects. The MPX 500's wrapper holds the law itself through `flock` and names `buildq`, so it passes; a project like it with no such word declines with `guards.build.queue`.
- **d-19, the notes are read only before there is code.** Once one source file exists, code decides and a word in a README adds nothing.
- **d-20, `packs` stays as it was.** It is what `update` reads back, and the noop test holds it. The lock gains `installed` beside it.
- **d-21, `ScopedNoDenormals` first, `readTransport` second.** The guard must hold before any DSP, and `readTransport` does none. The work order had it the other way; the hook takes both.
- **d-22, an unattended mode is a rule, not a change to the CLAUDE.md block.** The block is pinned by the noop test, and a rule reaches every install on `update`.
- **d-23, `doctor --strict` on a first source file.** It passes only once `doctor` does: the rules that govern that file need their tests, or `ruleTests` declining them with a reason. That is KF-31 holding, and the test proves the path.

## Group 4: what the build taught

- **d-24, a new rule, not a new check.** No pattern can tell a gate that writes the parameter from one that drives the input. The rule's Check names a test, so `doctor` asks for it once the rule governs UI source.
- **d-25, the version.** `package.json` ends at 1.1.0, as the work order says. `doctor` going red on update for rules with no test may count as breaking under the changelog's semver promise; `docs/1.1-report.md` puts that to the user before publishing.
