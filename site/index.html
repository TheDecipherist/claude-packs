A mistake stops at the write

Claude tries to write this into a Rust crate. The hook refuses it, the file is never written, and Claude gets the reason back. It returns a Result, and the write goes through. Nobody had to catch it in review.

src/parser.rs
pub fn parse(text: &str) -> u32 {
    text.parse::<u32>().unwrap()
}

Why use it

The whole workflow

Each session starts cold, the same mistakes come back, and code gets written twice. So the kit keeps what a session can't.

Mistakes stop at the write

A hook refuses a bad write before it reaches the disk, and says why. It never lands, so it never needs finding.

Nothing gets written twice

Copies, near copies and functions made again are refused, with what differs between them, so repetition turns into one template.

The project remembers

The plan, the bugs and the decisions live in plain files in the repo, so a new session picks up where the last one stopped.

Every bug makes it stronger

A bug starts with a test that fails for it, and the fix can become a check that refuses that mistake from then on.

"Done" gets measured

A step finishes on a test or a number, and a gate is seen to fail on a planted fault before anyone trusts it.

You can see what works

Every call and refusal is logged and judged, so you know which hooks earn their place.

Getting started

Memory

What a project keeps

Claude forgets between sessions, so everything worth keeping lives in files. Logs are never cleared: a full one rotates, and the history stays.

Testing

Strict about proof

  • A bug fix starts redShow the bug with a test that fails for that reason, then fix the code.
  • A test has to be able to failA gate is shown red on a planted fault, a mistake put in on purpose.
  • Tested once, on the templateAnything used twice is one template. One quick pass proves the instances really are it.
  • Only what the change reachesWhile working, a small change never costs a full test run.
  • The whole suite, onceIt runs on committed work, as the gate before landing, and a hook refuses it any earlier.
  • The guards are tested tooEvery hook has a selftest, every check proves its own examples, and doctor runs them all.

Work orders

Let it build on its own

A work order is a written brief a project can build from with nobody there. It takes the recommended choice, writes down every decision so you can overturn it, and resumes from a file when a session ends. A whole plugin, firmware map to finished panel, was rebuilt this way overnight.

docs/workorders/billing/workorder.md
## W2. The import

1. Read every record in `data/orders.csv` into the schema of W1.
2. Reject a bad row by name, with its line number. Never skip one silently.

**Done when:** all 41,206 rows of the sample load, the 12 known bad rows are each
rejected with the right reason, and a planted bad row turns the test red.

Every step ends with a number or a test. "Works" can't be measured, so it can't finish.
