# Put the ready standalone on the owner's rack (one job: the rack opens what the user would launch, described truly)

The owner keeps one rack page that launches every built synth: `synths.html`, generated by `tools/synths.py` in the rack repository (`guards.rack.repo` in `.claude/layout.json`, else `~/projects/eproms`). The owner, 2026-11-25: whenever a plugin's standalone is ready to test, it goes on the rack, without being asked. Read the rack repository's own CLAUDE.md section on the rack once before the first edit; its rules win over this skill.

<constraints>
Always do:
1. Run `node .claude/tools/rack-join.mjs check <the launched .app>`, the same app `can-the-user-open-it` proved. Exit 0 means the row is there and the rack opens that app: go to step 4.
2. "no row in UNITS": add one to `UNITS` in `<rack>/tools/synths.py`, in the table's own shape and order (uid, display name, maker, year, the project's folder name, blurb, the catalog's maker and model), beside its maker's other rows. The uid is short, lower case and new.
3. "the rack opens another app": add the unit to `APP_OVERRIDES` with the path to the launched app, or the (project, glob) form when the build folder holds one app, with a comment saying why the default glob misses it (another build folder, several apps, a leftover configuration).
4. Read the row's blurb against the project's state now (its stage, what is measured, what is not), and rewrite it when it is out of date. It says what is evidence and what is not: what works and was measured, and what is missing. A row that reads as a finished machine while parts are missing is worse than no row.
5. Run `node .claude/tools/rack-join.mjs write`: it regenerates `synths.html` and restarts the rack's server, which reads UNITS only at start. Then run `check` again and see exit 0.
6. Commit in the rack repository by name (`git add tools/synths.py synths.html`, `git commit -m "rack: ..." -- <paths>`), the message saying what joined or changed and how many units are built (`write` prints it), and push as that repository's rules say.
7. Say in the turn's report that the unit is on the rack, with the commit.

Never do:
- Edit or commit `tools/synths.py` while it holds another session's uncommitted change (`git -C <rack> status --short tools/synths.py`, then its diff): a commit by name would carry their row. Say the rack step waits for it, and do it in the next turn once the file is clean (seen in: supernova2_monitor, 2026-11-25, a Collider row in progress on the rack's branch).
- Edit `synths.html` by hand: the generator owns it.
- Put a unit on the rack whose standalone does not open, or leave a blurb that claims more than the project measured.
- Change another unit's row, or the generator's code, to fit this one: a fault in the generator is logged in the rack repository's own workflow bug log.
</constraints>
